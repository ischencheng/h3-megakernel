### Megakernel Plan

This plan covers H3 end to end, from text input to video and audio output, as one persistent launch. Part 1 lists every kernel we run today and whether we reuse it from a library or rewrite it. Part 2 describes the megakernel itself: the files to write, how it schedules work, and how it runs the existing kernels as tasks.

The numbers come from one 1344x768, 5 s request on the RTX PRO 6000 (`build/profiles/nsys-roulette-1344x768-ryan-20261110-201826/request.sqlite`). That request ran 53,656 kernels in about 30.8 s of GPU time:

| Stage | GPU time |
|---|---:|
| Text encoder | 0.02 s |
| DiT | 26.24 s |
| Video VAE | 4.46 s |
| Audio VAE | 0.03 s |

### Part 1: Kernels

**Use** means we take the library's source and turn it into a megakernel task. **Rewrite** means we write it ourselves in CUDA. Triton and torch kernels always need a rewrite, because a CUDA kernel cannot call them as device functions.

#### What we reuse

We take source from CUTLASS 2.x and 3.x, FlashInfer (the fused MLP and quantize kernels), fastvideo-kernel (attention) and FA2. We write everything else. About 90% of the time is in four kernels we reuse, so we have many rewrites to do, but each one is small.

### Part 2: The megakernel

#### Device side

The whole request runs as one launch with one CTA per SM. The RTX PRO 6000 has 188 SMs; check this on the GPU. Every task runs in the same CTA shape:

- **384 threads.** The CUTLASS SM120 cooperative GEMMs, `compute_attn_ws` and FlashInfer's MLP all use 3 warpgroups. The 128-thread kernels (FA2, CUTLASS 2) run 3 tiles at once, one per warpgroup, as the norm phase in `stages/dit/fi_mlp.py` does.
- **About 99 KB of shared memory**, the SM120 limit per block. Every task must fit. FlashInfer's MLP needs 94 KB, and the 6-stage INT8 GEMM is close to the limit.
- **168 registers per thread.** Tasks move registers between warpgroups with `setmaxnreg`, as the `ffn-megakernel` branch does.

Each CTA runs this loop:

```
loop:
  i = atomicAdd(&next_instr, 1)        // one global queue, in dependency order
  if i >= n: break
  wait:   one thread spins with ld.acquire.gpu on each (counter, value),
          then fence.proxy.async if the task loads with TMA, then __syncthreads
  switch (instr.opcode): task_X(instr, params[instr.op], smem)
  signal: __syncthreads; one thread runs fence.proxy.async if the task stored with TMA,
          then red.release.gpu.add on the instruction's signal counters
```

We use one global queue rather than a list per SM. An instruction only waits on instructions earlier in the queue, and resident CTAs have already claimed those, so the launch cannot deadlock. Each CTA takes the next instruction when it is free, so the load balances itself. If we later want control over which SM reads which data, we can switch to static lists per SM, as HazyResearch/Megakernels does. Prefetching the next instruction from a separate warp is also a later optimization.

The kernel reads three structures from global memory:

- **Instruction table.** Each instruction takes about 64 B: an opcode, the id of the op instance, a range of tiles, up to 4 (counter, value) pairs to wait on and up to 2 counters to signal.
- **Parameter table.** The host builds one entry per op instance: pointers, shapes, precomputed CUTLASS `Params`, and TMA descriptors aligned to 64 B.
- **Counters.** Each op instance has its own counters, so no counter is reused across steps. We zero them once per request. The program is fully unrolled: 8 steps x 50 blocks x about 15 ops x their tiles comes to tens of thousands of instructions, a few MB.

#### Turning an existing kernel into a task

- **Persistent kernels** (CUTLASS 3, `compute_attn_ws`, FlashInfer's MLP):
  - `__global__` becomes `__device__`.
  - The kernel's tile scheduler is replaced so it runs the instruction's tiles instead of looping from `blockIdx`. For CUTLASS, this is a custom `InstructionTileScheduler`.
  - Each `__grid_constant__ CUtensorMap` parameter becomes a reference into the parameter table.
  - Shared memory comes from one shared buffer, and each task initializes its mbarriers again.
- **Kernels that compute one tile per CTA** (CUTLASS 2 `Kernel2`, FA2): the task calls the kernel body with tile coordinates in place of `blockIdx`, looping over the instruction's tile range.

As in `fi_mlp.py`, we patch the installed libraries' source at build time, so no third-party code is committed to our repo.

#### Host side

The host side is a Python compiler. It runs once per resolution and duration, because every shape is fixed and only the data changes. The VSA block lists are data too: the attention task reads them from global memory.

1. Build the graph of ops for the whole model: text encoder, then 8 x 50 DiT blocks, then the VAE tiles, then the audio VAE.
2. Split each op into tiles, and record the tensor regions each tile reads and writes.
3. Find dependencies where one tile reads a region another tile writes, and compute the count each counter must reach.
4. Order the tiles so every tile comes after the tiles it depends on. A cost model built from the nsys numbers can interleave independent work.
5. Plan memory ahead of time, reusing activation buffers once they are no longer needed. The weights stay resident.
6. Build all CUTLASS parameters and TMA descriptors.
7. Write out the instruction table.

#### Files to write

```
skeleton/
  include/mk/
    megakernel.cuh      persistent loop: fetch, wait, opcode switch, signal
    instr.cuh           Instr struct and opcode enum (generated by the host)
    sync.cuh            acquire and release on counters, proxy fences
    smem.cuh            shared-memory buffer, mbarrier reset, setmaxnreg helpers
    trace.cuh           timestamps per instruction (like the ffn-megakernel trace)
  tasks/
    gemm_nvfp4.cuh      CUTLASS 3 SM120 block-scaled GEMM + InstructionTileScheduler (text encoder, DiT linears)
    mlp_fi.cuh          generated from FlashInfer (port the patching in fi_mlp.py)
    attn_fp4_sparse.cuh compute_attn_ws, converted to a task
    attn_fa2.cuh        FA2 (text encoder BF16, VAE FP16)
    gemm_int8.cuh       CUTLASS 2.x (VAE)
    conv1d.cuh          implicit-GEMM convolutions for the audio VAE
    elementwise.cuh     norm, modulate, RoPE, quantize, gated residual, scheduler step, layout copies
    vsa_select.cuh      pooling, top-k, block lists
  host/
    graph.py            op graph
    lower.py            ops to tiles with read and write regions
    deps.py             dependencies and counter counts
    schedule.py         instruction order
    memory.py           memory plan
    params.cpp          CUTLASS params and TMA descriptors
    emit.py             instruction table
  model/h3.py           builds the full H3 graph
  build.py              patches third-party source and compiles it at run time
  bindings.cpp
  tests/                fake-task smoke test, then one test per task against the stored tensors
```

#### Build order

1. The skeleton with fake tasks, to check the queue and the counters.
2. `gemm_nvfp4` on its own, compared with `mm_fp4`.
3. One DiT block: the GEMMs, the MLP, attention and the elementwise rewrites.
4. All 50 blocks, then the 8-step loop.
5. The video VAE.
6. The text encoder.
7. The audio VAE.

Until a part is ported, it runs as separate launches, as Milestone 3 allows.

#### Risks

- Four large kernels take most of the time, so launch overhead is not where the time goes. The saving has to come from removing the ~6 s of small kernels and from overlapping work across ops and stages.
- The two hardest pieces are converting the sparse FP4 attention kernel and writing CUTLASS's custom tile scheduler.
- Using fastvideo-kernel, SageAttention3, FlashInfer or CUTLASS source needs approval on Ed.
